# 通用工程原则 (Principles)

> 跨领域的底层信条。每个 package 的规范都是这些原则在特定领域的具体化。
> 新增 package 前，先看它是否违背了这里的某一条。

---

## 1. 克制优于堆砌

能少就不要多。一个页面一个主操作，一个函数一个职责，一个服务一个边界。
复杂度是负债，不是资产。

## 2. 内容 / 意图优先

界面让内容成为主体，代码让意图成为主体。
读起来像「又在调 API」而不是「又在堆配置」。

## 3. 语义化，不写死

颜色用语义 Token 而非十六进制；配置用语义命名而非魔法数字。
换个主题 / 环境时，只改一处定义，不动一百处引用。

## 4. 约定优于配置

目录结构、命名、分层先定死，后来者照抄即可。
减少「这个该放哪」的决策成本，就是减少出错面。

## 5. 可观测，可回退

日志结构化、关键路径有埋点、改动可灰度可回滚。
出问题时能定位，上线后能退回来。

## 6. 规范优先于代码

文档是本体，代码是规范的可执行示例。
先想清楚「为什么这么做」，再写「怎么做」。

## 7. 纯拷贝起步，按需升级

能 clone 拷贝解决就不要急着抽象成依赖包。
等真正被多处高频复用、需要版本锁定时，再封装。避免过早抽象。

---

> 各领域如何落地这些原则，见对应 `packages/<name>/README.md`。
