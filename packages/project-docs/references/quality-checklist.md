# 项目文档质量检查清单

## 范围与需求

- [ ] 一句话定义能够说明用户、问题和结果。
- [ ] MVP 范围与非目标清晰，没有互相冲突。
- [ ] 每项核心功能有稳定需求 ID。
- [ ] 每项核心需求都有可验证的验收条件。
- [ ] 异常流程不是只写“返回错误”。
- [ ] 非功能要求包含可度量目标或明确约束。

## 领域与系统设计

- [ ] 领域术语在所有文档中含义一致。
- [ ] 核心实体、关系、状态和业务不变量已定义。
- [ ] 模块职责说明了“负责什么”和“不负责什么”。
- [ ] 依赖方向明确，没有循环描述。
- [ ] 同步、异步和长任务边界明确。
- [ ] 关键故障、降级、重试和回退策略已说明。
- [ ] 项目目录结构来源于模块设计，而非反向决定架构。

## API 与数据

- [ ] 接口鉴权、版本、错误、分页、幂等约定统一。
- [ ] API 名称与领域模型一致。
- [ ] API 不直接泄露无必要的内部实现细节。
- [ ] 数据表能够支持核心业务流程。
- [ ] 主键、外键、唯一约束和关键索引有理由。
- [ ] 数据迁移、保留、删除和备份策略明确。
- [ ] 临时缓存与长期事实数据已区分。

## 安全与合规

- [ ] 信任边界和敏感资产已识别。
- [ ] 身份认证与权限授权被分开描述。
- [ ] 密码、API Key、Cookie、Token 等不以明文记录或输出日志。
- [ ] 输入校验、限流和滥用防护有明确位置。
- [ ] 第三方服务、开源许可证和数据使用边界已记录。
- [ ] 未把法律判断写成未经确认的事实。

## 测试与交付

- [ ] 核心需求可追踪到测试场景。
- [ ] 正常、边界和失败路径均有测试方案。
- [ ] 外部依赖变化有契约或回归测试策略。
- [ ] 发布质量门槛明确，不只依赖覆盖率数字。
- [ ] Roadmap 的里程碑具有交付物和完成条件。
- [ ] Progress Log 记录实际历史而非复制 Roadmap。

## 文档治理

- [ ] 同一事实没有在多处重复完整维护。
- [ ] 假设、未知项和暂定结论均有显式标签。
- [ ] 重要架构取舍有 ADR，普通细节未滥用 ADR。
- [ ] 已接受 ADR 的变更通过新 ADR 取代。
- [ ] 文档包含最后更新时间和负责人。
- [ ] 没有为了填模板而产生无意义的长段落。
