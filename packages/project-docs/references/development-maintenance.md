# 开发中文档维护

用于已经进入开发阶段的项目。目标不是每次改代码都重写文档，而是让需求、设计、实现事实、计划和历史在有意义的变化后保持一致。

## 确认当前状态

先读取与本次请求有关的最小证据集：已有文档、工作区 diff、相关源码和测试，以及必要的配置、契约或 migration。

区分四种状态：

- **Planned**：需求或设计已确认，但实现尚未开始；
- **In Progress**：存在部分实现，尚未达到验收条件；
- **Implemented**：代码和验证证据表明行为已经落地；
- **Diverged**：文档与实现冲突，尚不清楚哪一方代表当前意图。

不要因为存在接口、空模块、未运行的测试或计划文字就把功能标成完成。用户明确说明的开发状态优先；仓库证据用于验证和发现矛盾。

## 选择维护动作

### 文档缺失或落后于已有实现

使用 Formalize：以代码、配置、schema、migration 和测试为实现事实，补充最少必要文档。保留原有有效内容，并明确记录“当前实现”和“预期设计”的偏差。

### 准备开发新需求

先更新 Requirements；再按影响更新 Domain、System、API、Data、Security、Testing 和 Roadmap。只有阻塞实现的产品或架构问题需要先询问，非阻塞项可以显式标记后继续。

### 实现正在进行或刚完成

- 只同步本次变化影响的文档；
- API 字段以 OpenAPI/契约为准，数据库结构以 schema/migration 为准；
- 达到验收条件后才能把需求或里程碑标记为完成；
- 有意义的结果追加到 Progress Log，同时更新 Roadmap 当前状态；
- 普通重构、格式化和局部实现细节不写进 Progress Log。

如果用户只要求维护文档，不要擅自修改实现。如果用户同时要求开发，则在实现前检查相关文档，完成并验证代码后再同步受影响文档。

### 重要技术取舍

跨模块、难逆转、成本高或有争议的决定使用 ADR。普通库调用、局部重构和可轻易替换的实现细节不创建 ADR。

## 处理冲突

发现文档与实现不一致时：

1. 列出双方证据和实际影响；
2. 能从用户要求、测试或已接受 ADR 判断当前意图时，更新过期一方；
3. 无法判断时保留双方，不静默选择，并把问题标记为阻塞或 `[待确认]`；
4. 不通过重写 Progress Log 或已接受 ADR 来掩盖历史偏差。

## 完成检查

- 本次变更影响的需求、领域、接口、数据、安全和测试内容一致；
- 文档状态与实际实现状态一致；
- Roadmap 是当前计划，Progress Log 是实际历史；
- 已完成项有代码或测试等验证证据；
- 未受影响的文档没有被机械改写；
- 剩余假设、冲突和下一步已明确报告。
