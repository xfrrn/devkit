# 新项目初始化访谈

用于 `Initialize` 模式：用户可能只提供一句项目想法，Skill 负责把它引导成能够开始开发的文档基线。

## 访谈原则

1. 先提取用户已经说明的内容，不重复询问。
2. 先理解产品，再讨论技术；不要用技术选型代替需求分析。
3. 一次集中询问当前真正阻塞文档落地的问题，避免逐题审讯。
4. 用户不确定时，给出少量有实际差异的选项和推荐理由。
5. 用户授权代为决定时，选择简单、可逆的方案，并标记为 `[暂定]` 或记录为明确决策。
6. 非阻塞未知项可以进入文档的 `待确认问题`；会改变 MVP、核心流程、数据边界或架构的未知项必须先确认。
7. 访谈阶段只创建文档，不开始实现代码，除非用户同时明确要求开发。

当阻塞信息仍缺失时，不要先运行初始化脚本或生成一批待确认模板；只有用户明确要求空白脚手架时可以直接复制模板。

## 最小信息集

从用户描述中提取以下内容，只询问缺失且重要的部分：

- 项目名称和一句话定义；
- 要解决的问题、目标用户和当前替代方案；
- MVP 必须交付的结果和明确非目标；
- 一至三个核心用户流程及成功结果；
- 核心业务对象、状态和关键业务规则；
- 目标平台、外部集成、部署或组织约束；
- 数据来源、敏感性、保留和删除要求；
- 性能、可靠性、安全或合规方面的硬约束；
- 当前已接受的技术决定，以及仍可选择的部分；
- 负责人、当前阶段和第一个可交付里程碑。

不要机械询问全部条目。简单项目可以用更少问题；只有在答案会改变设计时才继续追问。

## 对话流程

### 1. 复述理解

用几句话总结已知的用户、问题和预期结果，指出最关键的缺口。不要把复述写成已批准需求。

### 2. 集中提问

提出一组简短问题，优先顺序为：

```text
目标与用户 → MVP 与非目标 → 核心流程 → 数据与边界 → 约束与交付
```

不要一开始就询问框架、数据库或云服务，除非用户已给出技术约束或项目本身以技术选型为目标。

### 3. 处理不确定性

- 用户明确回答的内容视为事实或决定。
- Skill 推导但用户尚未确认的内容标记 `[假设]`。
- 为推进设计临时选择的可逆方案标记 `[暂定]`。
- 无法安全推导的内容标记 `[待确认]`。

如果用户说“你来决定”，给出推荐方案及其代价；跨模块、难逆转或有明显争议的选择使用 ADR。

### 4. 生成开发前基线

先完成 Brief 和 Requirements，再根据项目实际内容选择其他文档：

| 条件 | 文档 |
|---|---|
| 存在多个业务对象、状态或不变量 | Domain Model |
| 需要说明模块边界、运行方式或外部依赖 | System Design |
| 存在客户端/服务、服务间或第三方契约 | API Contract |
| 存在持久化、迁移、缓存或数据生命周期 | Data Design |
| 存在身份、权限、敏感数据或合规约束 | Security and Compliance |
| 存在需要验证的非平凡行为 | Testing Strategy |
| 开发分多个可交付阶段 | Roadmap |
| 已经发生有意义的项目工作 | Progress Log |
| 已接受重要且难逆转的选择 | ADR |

不要因为模板存在就创建空文档。初始化脚本的三份核心模板只是起点，不是 Initialize 模式的完成条件。

## 开发就绪检查

初始化完成前确认：

- 目标用户、问题、MVP 和非目标没有相互冲突；
- 核心流程包含正常、边界和失败结果；
- 核心需求有可验证的验收条件；
- 领域术语和业务规则足以约束实现；
- API、数据和安全文档只在适用时存在，并与需求一致；
- 第一个里程碑可以拆成具体开发任务；
- 没有要求实现者临时发明产品规则的阻塞未知项；
- 尚未开始的工作没有被写进 Progress Log 作为历史。

如果仍有阻塞问题，先向用户确认；否则写入文档并报告非阻塞假设和下一步。
